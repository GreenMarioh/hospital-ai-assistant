# Decisions & Assumptions
- **Python 3.14** (spec said 3.12): the dev host only has 3.14; all dependencies install cleanly on it. Images use `python:3.14-slim`.
- **Rootless Docker** used on the dev host (no sudo). Postgres published on host port 5433 because 5432 is taken.
- **Background jobs: APScheduler** in a dedicated worker process. Simpler than Celery+Redis; deduplication via the `notifications` table so restarts never double-send.
- **Caddy** replaces Nginx for TLS (automatic Let's Encrypt renewal).
- **RAG**: Postgres full-text search over `knowledge_base/*.md` (pgvector deferred).
- **Field encryption**: Fernet with key from env for insurance ID.
- **Least privilege DB**: `hospital_app` runtime role (DML only); `hospital_migrator` owns schema and runs Alembic.
- **Clinical data least privilege**: visits, prescriptions and AI summaries are readable only by the patient and by doctors with an appointment/visit relationship; admin and reception staff are excluded. Staff/admin see demographics; staff also upload and view documents. Unauthorized object access returns 404 to avoid leaking existence.
- **Versioning**: every edit snapshots the previous state into `record_versions` (immutable, with editor id) and bumps `visits.version`.
- **Documents**: PDF/PNG/JPEG only, 10 MB, magic-byte check, real ClamAV daemon TCP streaming protocol (`INSTREAM`), downloads via 5-minute signed links; deletes are soft.
- **AI safety design**: rule-based red flags run before and independently of the LLM, are sticky per conversation, and short-circuit it (no LLM call on emergency). Output guard replaces replies that diagnose or recommend medication. Booking assistant tools are read-only; `propose_booking` only stores a proposal and the patient must call `/api/ai/booking/confirm`.
- **AI resilience**: 30 s timeout, 3 attempts with exponential backoff on 429/5xx/connection errors (not on 4xx), circuit breaker (5 failures, 60 s), degraded deterministic behaviour for triage, FAQ and briefings; booking chat returns 503 pointing to manual booking.
- **AI evals & Clinical Review**: `python -m app.ai.evals.run [--live]`. Formal clinical review conducted under Manchester Triage System (MTS) and Emergency Severity Index (ESI) frameworks; evaluation dataset expanded to 60 benchmark cases covering sepsis, stridor, acute aortic syndromes, retinal occlusion, and complex trauma. The deterministic rule engine achieves 100% emergency recall (23/23) and 0% false positives (0/37) offline (see `backend/app/ai/evals/CLINICAL_REVIEW.md`). Live LLM eval run 2026-11-08 on `gemini-3.5-flash-lite`: urgency 80%, department 77%, one under-triage (u12); see `docs/TEST_REPORT.md`.
- **Model**: Google Gemini through the `google-genai` SDK, two tiers routed by purpose in `app/ai/client.py` (`FLASH_PURPOSES`). `GEMINI_MODEL` (default `gemini-3.5-flash-lite`) handles triage, briefings and visit summaries; `GEMINI_FLASH_MODEL` (default `gemini-3.1-flash-lite`) handles the booking tool loop and FAQ, where latency matters more. No sampling parameters are sent; `GEMINI_THINKING_LEVEL` / `GEMINI_FLASH_THINKING_LEVEL` are optional. Structured calls request `application/json` output and are still validated with Pydantic. Thinking tokens count against Gemini's output limit, so the client adds headroom to `max_output_tokens`. The function-call parts (including thought signatures) are echoed back verbatim during the booking tool loop, as Gemini 3 requires.
- **Redis is used only for shared rate-limit counters** (slowapi storage) so limits hold across the 4 API workers. Jobs stay on APScheduler (no Celery), as decided above.
- **Argon2id parameters**: OWASP minimum profile (19 MiB, t=2, p=1) instead of the library default (64 MiB, p=4); the default made login the dominant CPU cost under load. Hashing runs in a thread pool.
- **Multi-Factor Authentication (MFA)**: RFC 6238 TOTP two-factor authentication implemented with zero external dependencies via Python standard library `hmac`/`secrets`. Short-lived signed tickets prevent MFA bypass.
- **Token storage & Cookie Hardening**: Access tokens are kept in client memory only; rotating refresh tokens are stored in secure, `httpOnly`, `SameSite=Lax` cookies with path restriction (`/api/auth`). Per-request dynamic CSP nonces with `strict-dynamic` protect Next.js frontend against XSS.
- **Audit logging**: Runs asynchronously after response transmission via dedicated connection pool. Entries are cryptographically chained with SHA-256 (`prev_hash` -> `entry_hash`) and support append-only JSONL streaming for SIEM verification.
- **Production same-origin routing**: Caddy serves the SPA and `/api/*` on one origin, so the production frontend image is built with an empty `NEXT_PUBLIC_API_URL` and needs no CORS.
- **Docker inline env comments**: `.env` files must not contain inline comments (compose treats them as values); found by a clean-clone test.
- **Admin cannot read clinical notes** and reception cannot either (least privilege); admin still has data export/erasure endpoints, which are audit-logged.
- **Phase 10 status**: the live deployment (domain, DNS, VPS, registry) was **not performed**: it needs credentials/infrastructure only the owner has. Everything it needs was built and rehearsed locally against the production compose file: HTTPS via Caddy, migrations, deploy script, smoke test (register -> login -> book -> AI triage -> admin dashboard), automatic rollback of a deliberately broken release, and an encrypted backup with a tested restore. `provision.sh` (firewall, Docker, fail2ban, cron) has not been executed on a real VM.
- **Model defaults are free-tier models**: the project key is free tier, where Pro models are unavailable, Gemini 4 Argon has zero quota, `gemini-3.5-flash` is capped at 20 requests/day and 3.7/3.8 Flash exceed the 30 s timeout. Defaults are therefore the two Flash-Lite models (separate quotas). On a paid key, set `GEMINI_MODEL` to `gemini-3.5-flash` or a Pro model and re-run the eval. Tool-calling, structured-output and degradation behaviour are tested with a scripted fake client, not the live API.
